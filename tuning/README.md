# Aurora tuning bundle

Aurora build 1 shipped the jar and nothing else — no config, no start script. This
folder is that missing piece. Everything here was generated by actually running
Aurora 26.2, edited, and then booted again to confirm the server still starts
cleanly with it.

## What a server can and cannot do about ping

Ping is round-trip time. Most of it is the physical distance between the player
and the machine, plus whatever their ISP does on the way. **No server jar can
change that**, and anything claiming otherwise is selling something.

What a server *can* control is the part it adds on top:

- **How long a packet waits before the server gets to it.** If a tick takes
  60ms, packets sit in a queue for up to 60ms before anyone looks at them.
- **How much data the server sends back.** Saturating a player's downstream
  makes everything behind it queue up.
- **GC pauses.** A 200ms stop-the-world collection is 200ms of frozen server
  for every player at once, regardless of their connection.

Every setting below targets one of those three. None of them shorten the wire.

## What is changed, and why

### `config/aurora-server.yml` — networking

These are Aurora/CanvasMC's own features. All five ship **off** by default; this
bundle turns them on. The descriptions in the config file are upstream's.

| Setting | Now | Why |
|---|---|---|
| `filter-velocity-packet` | `true` | Upstream's note on this option says entity velocity packets "can often consume major amounts of network usage, often being up to 60% on large production servers" and that filtering them keeps the vanilla visual result. That figure is upstream's, measured on their servers, not ours. |
| `filter-move-packets` | `true` | Drops move packets that would not have changed anything on the client. Less data out. |
| `alternative-player-list-tick` | `true` | Splits players into buckets so the playerlist tick is spread out instead of landing in one tick. Trades a slightly staler tab list for a flatter tick graph. |
| `purpur-alternative-keepalive` | `true` | Sends a keepalive every second and only times a player out if *none* got a response in 30s. Directly relevant on a lossy connection: one dropped packet stops being a disconnect. |
| `flush-location-while-knockback` | `true` | From Leaf. Syncs the player immediately on knockback, so combat feels less rubber-bandy. |

### `server.properties`

| Setting | Default | Now | Why |
|---|---|---|---|
| `view-distance` | 10 | 8 | Chunk and entity traffic scales with the area each player tracks. This is the single biggest lever on bytes-per-player. |
| `simulation-distance` | 10 | 6 | Shrinks what actually ticks. Less work per tick, shorter ticks. |

Both are conservative. If you are on a good host with headroom, put them back
up — they are the first thing to raise, and the first thing to drop if the
server is struggling.

`network-compression-threshold` is deliberately left at the default `256`.
Lowering it compresses more packets (less bandwidth, more CPU on both ends);
raising it does the reverse. Which one helps depends on whether your bottleneck
is the network or the CPU, so there is no correct value to ship.

### `start.sh`

Aikar's flags, the same set Atlas ships, for the same reason: they exist to keep
G1GC pauses short, and GC pauses are the one source of ping spikes the server
fully controls.

Two deliberate choices carried over from Atlas:

- **`-XX:+AlwaysPreTouch` is left out.** It commits and zeroes the whole heap
  before the server starts, which makes every boot noticeably slower. Add it
  back if you would rather pay that cost up front.
- **`-Xms` equals `-Xmx`.** A heap that resizes at runtime does so by pausing,
  and it picks the busiest moments to do it.

One addition Atlas does not need:

- **`--add-modules=jdk.incubator.vector`** — Aurora checks for SIMD support at
  startup and, without this flag, logs `SIMD operations are available for your
  server, but are not configured!`. With it, the same run logs `SIMD operations
  detected as functional. Will replace some operations with faster versions.`
  It must come before `-jar`, which is where the script puts it.

Memory is set to `4G`. Region threading uses more than single-threaded Paper for
the same player count. Set it to what the machine actually has, minus room for
the OS — do not set it higher than physical RAM.

## Using it

Copy `server.properties`, `start.sh` and `config/` next to your `Aurora-26.2.jar`,
set `eula=true` in `eula.txt`, then:

```bash
./start.sh
```

`config/aurora-server.yml` here is a full generated file from Aurora 26.2. If you
already have one, copy just the `networking:` block across instead of overwriting
your own settings.

## What was verified

On an Apple Silicon machine, JDK 25.0.2, Aurora 26.2 build 1:

- Server boots clean with this config — `Done (6.771s)!`, no config errors.
- Boots clean via `start.sh` — `Done (26.373s)!`, no errors. (Longer because of
  the bigger heap and the GC flags; this is startup only, not runtime.)
- SIMD flips from "not configured" to "functional" with the vector flag.

**No ping, TPS or throughput numbers are published here, because none were
measured.** The settings above are chosen for a documented mechanism, not a
benchmarked result. If you measure something on real hardware with real players,
that would be worth adding — with the hardware and method written down next to it.
